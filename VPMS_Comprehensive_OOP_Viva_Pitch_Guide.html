Chapter 2: Pillar 1 — Encapsulation in Depth
2.1 Academic Definition & Invariant Protection model/ParkingSlot.java • model/ParkingSession.java

Theoretical Definition: Encapsulation is the mechanism of wrapping data (variables) and code acting on the data (methods) together as a single unit, while restricting direct access to the internal components using private access specifiers. It is also known as Data Hiding.

Why Encapsulation is Essential (The Invariant Problem): If an outside class could execute slot.status = SlotStatus.AVAILABLE; directly, a slot could be marked free while a car is physically parked in it! Encapsulation prevents corrupted object state.

// From model/ParkingSlot.java:
@Entity
@Table(name = "parking_slots")
public class ParkingSlot {

    // 1. DATA HIDING: All fields are private
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long slotId;

    @Column(nullable = false, unique = true)
    private String slotNumber;

    @Enumerated(EnumType.STRING)
    private SlotStatus status = SlotStatus.AVAILABLE;

    // 2. CONTROLLED ACCESSORS WITH VALIDATION:
    public SlotStatus getStatus() { 
        return this.status; 
    }

    public void setStatus(SlotStatus status) {
        if (status == null) {
            throw new IllegalArgumentException("SlotStatus invariant violation: status cannot be null!");
        }
        this.status = status;
    }
}
Memory Architecture Insight (Stack vs Heap): When ParkingSlot slot = new ParkingSlot(); runs, the reference variable slot lives on the Thread Stack (holding a 64-bit memory address). The actual object with its private fields (slotId, slotNumber, status) is allocated inside the JVM Heap. Encapsulation ensures that stack code cannot directly mutate heap bytes without traversing public method frames.

Chapter 5: Pillar 4 — Polymorphism in Depth
5.1 Compile-Time (Overloading) vs. Runtime (Overriding) model/Vehicle.java • service/ParkingService.java

Theoretical Definition: Polymorphism (from Greek: "having multiple forms") is the ability of an object, reference, or method to take on different behaviors depending on context.

A. Compile-Time Polymorphism (Method Overloading / Static Binding):

Occurs within the same class/interface where methods share the exact same name but differ in: (1) Number of arguments, (2) Data types of arguments, or (3) Order of parameters.

// In interfaces/ParkingFeeCalculator.java & model/Vehicle.java:
// Overload 1: Standard billing by hours
public double calculateParkingFee(long durationHours);

// Overload 2: Billing with promotional discount percentage
public double calculateParkingFee(long durationHours, double discountPercentage);

// Overload 3: Wrapper class unboxing demonstration
public double calculateParkingFee(Integer hoursWrapper);

B. Runtime Polymorphism (Method Overriding & Dynamic Method Dispatch):

Occurs when a subclass provides a specific implementation of a method declared in its parent class with the exact same signature. The method to execute is resolved at runtime by the JVM.

// IN SERVICE LAYER (service/ParkingService.java - Line 168):
// 1. Reference variable type is the ABSTRACT SUPERCLASS:
Vehicle vehicle = session.getVehicle();

// 2. DYNAMIC METHOD DISPATCH IN ACTION:
// The compiler only checks that `Vehicle` has `calculateParkingFee()`.
// At RUNTIME, the JVM inspects the object header on the heap:
//   - If it's a `Bike`  -> Executes Bike.calculateParkingFee()  (₹20 first hr, ₹10/hr)
//   - If it's a `Car`   -> Executes Car.calculateParkingFee()   (₹30 first hr, ₹20/hr)
//   - If it's a `Truck` -> Executes Truck.calculateParkingFee() (₹50 first hr, ₹30/hr)
double fee = vehicle.calculateParkingFee(durationHours);
JVM vtable (Virtual Method Table) Explanation: "When the JVM executes vehicle.calculateParkingFee(), it does not do an if-else check. Every loaded class in the JVM maintains a Virtual Method Table (vtable) containing pointers to its executable bytecode. At runtime, the JVM looks up the object's runtime class in the Heap, reads its vtable, and jumps directly to that specific method pointer."

6.2 final vs static vs volatile vs transient Language Keywords

• final: Applied to variables (makes them immutable constants), methods (prevents child classes from overriding), and classes (prevents inheritance, e.g. java.lang.String).

• static: Belongs to the class rather than instances. Allocated once in JVM Metaspace. Used for shared constants (CAR_FIRST_HOUR_RATE) and utility methods.

• volatile: In ParkingMonitor.java, private volatile boolean running = true; ensures memory visibility. Multi-core CPUs store variable copies in high-speed hardware L1/L2 caches. volatile forces all threads to read/write directly to main RAM, preventing cache incoherence.

• transient: Prevents a field from being serialized or saved to the database. In TwoWheeler.java, @Transient private int engineCapacityCc; is ignored by Hibernate ORM.

6.3 Static Nested vs. Non-Static Inner Classes demo/NestedClassDemo.java • model/ParkingLot.java

• Static Nested Class (ParkingLot.ParkingStatistics): Does NOT require an outer class instance. Instantiated via new ParkingLot.ParkingStatistics(). Cannot access non-static outer members.

• Non-Static Inner Member Class (ParkingLot.SlotManager): Bound to an outer class instance. Has direct implicit access to outer class private fields (parkingGrid).

6.4 Parameter Passing: Why Java is Strictly 100% Pass-by-Value demo/ArgumentPassingDemo.java

• Primitives (int, double): A raw bitwise copy of the value is pushed onto the called method's stack frame. Modifying it has ZERO effect on the caller.

• Objects: Java passes a COPY OF THE 64-BIT REFERENCE POINTER by value. Reassigning the pointer (vehicle = new Vehicle()) does NOT affect the caller. However, mutating the object via the copied pointer (vehicle.setOwnerName("Bob")) affects the shared heap object!

Chapter 7: Concurrency & Multithreading Architecture
7.1 Thread Lifecycle & Implementation Approaches threads/ParkingMonitor.java • threads/ParkingSessionMonitor.java

Thread Lifecycle States: NEW → RUNNABLE → BLOCKED / WAITING / TIMED_WAITING → TERMINATED.

• Approach 1 (Extending Thread): public class ParkingMonitor extends Thread. Overrides run(), configured with setPriority(Thread.NORM_PRIORITY - 1), and set as a background daemon (setDaemon(true)).

• Approach 2 (Implementing Runnable): public class ParkingSessionMonitor implements Runnable. Preferred in enterprise design because Java allows implementing multiple interfaces while preserving single inheritance.

• Thread.start() vs Thread.run(): Calling run() executes synchronously in the caller thread. Calling start() requests the OS thread scheduler to spin up a new OS thread and invoke run() asynchronously.

7.2 Thread Synchronization: Producer-Consumer Queue threads/ParkingRequestQueue.java

To safely buffer vehicle requests, ParkingRequestQueue implements the classic Producer-Consumer Pattern using Java monitor locks:

public class ParkingRequestQueue {
    private final Queue<String> queue = new LinkedList<>();
    private final int CAPACITY = 10;

    // PRODUCER METHOD:
    public synchronized void enqueue(String vehiclePlate) throws InterruptedException {
        while (queue.size() == CAPACITY) {
            wait(); // Releases lock and sleeps until buffer space frees up
        }
        queue.add(vehiclePlate);
        notifyAll(); // Wakes up consumer threads
    }

    // CONSUMER METHOD:
    public synchronized String dequeue() throws InterruptedException {
        while (queue.isEmpty()) {
            wait(); // Sleeps until new vehicle request arrives
        }
        String vehicle = queue.poll();
        notifyAll(); // Wakes up producer threads
        return vehicle;
    }
}

8.1 Throwable Hierarchy & Custom Unchecked Exceptions exception/SlotFullException.java • exception/GlobalExceptionHandler.java

Hierarchy: java.lang.Throwable → (1) Error (serious JVM failures: OutOfMemoryError, StackOverflowError) and (2) Exception.

• Checked Exceptions: Inherit directly from Exception (e.g. IOException). Must be declared with throws or caught with try-catch at compile time.

• Unchecked Exceptions: Inherit from RuntimeException. Represent programming bugs or logical domain failures. Our project implements:

// Custom Exception Definition:
public class SlotFullException extends RuntimeException {
    public SlotFullException(String message) {
        super(message);
    }
}

// Global Spring Controller Advice:
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(SlotFullException.class)
    public ResponseEntity<ErrorResponse> handleSlotFull(SlotFullException ex) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
                             .body(new ErrorResponse("SLOT_FULL", ex.getMessage()));
    }
}

Q4: What is Constructor Chaining and where is it used?
Answer: Constructor chaining is the sequence of invoking constructors from subclass to superclass using super(). In Car.java, the constructor calls super(vehicleNumber, ownerName, phone), which delegates to FourWheeler, which in turn calls Vehicle, ensuring safe base object initialization before subclass fields are set.

Q5: Why did you use interfaces if abstract classes already exist?
Answer: Java prohibits multiple inheritance of classes to prevent ambiguity (the Diamond Problem). Interfaces allow Multiple Inheritance of Type. In our system, Vehicle implements both ParkingFeeCalculator (for billing contracts) and PrintableReceipt (for formatting output). Interfaces also support Java 8 default methods for reusable fallback behavior.
Interfaces
Q6: How does Java handle argument passing? Prove it using your codebase.
Answer: Java is strictly 100% Pass-by-Value. For primitives, a copy of the literal value is passed. For objects (demonstrated in demo/ArgumentPassingDemo.java), Java passes a copy of the memory address reference. Reassigning the reference pointer inside a method has no effect on the caller, but modifying object properties mutates the shared heap object.

Q7: What is the difference between Thread.start() and Thread.run()?
Answer: Calling run() simply executes the method body synchronously on the current thread without spinning up a new thread. Calling start() registers a new execution context with the operating system thread scheduler, transitions the thread to RUNNABLE, and asynchronously executes run().

Q8: What is the purpose of the volatile keyword in your background thread?
Answer: In ParkingMonitor.java, private volatile boolean running = true; guarantees memory visibility across threads. Multi-core CPUs cache variables in L1/L2 hardware caches. Declaring it volatile forces all threads to bypass local caches and read/write directly to main RAM, ensuring the thread stops immediately upon shutdown.
